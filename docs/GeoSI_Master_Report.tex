% ── ABSTRACT ──
\begin{abstract}
\noindent This report presents GeoSI (Geospatial Superintelligence), a conversational AI system that translates natural language queries into multi-step GIS workflows. The system is built around three clean architectural surfaces: (1)~a universal, framework-free engine core with 127 auto-discovered tools, (2)~a QGIS desktop plugin providing an interactive chat interface synchronized with the native layers panel, and (3)~a FastAPI REST server with a portable GeoPandas backend enabling QGIS-independent spatial analysis. The engine employs a five-stage pipeline---normalization, intent classification, workflow planning, tool execution, and result generation---with an LLM priority chain (Ollama $\rightarrow$ Gemini $\rightarrow$ Anthropic $\rightarrow$ keyword rules) that ensures reliable operation in both online and offline environments. Case studies using Kerala administrative boundaries and school point datasets demonstrate buffer, clip, intersect, and attribute join operations through natural language commands. The architecture establishes a foundation for geospatial superintelligence by decoupling spatial reasoning from any specific GIS platform.
\end{abstract}

\chapter{Introduction}

\section{Motivation}
Geographic Information Systems (GIS) are essential tools for spatial analysis, urban planning, environmental monitoring, and disaster management. However, traditional GIS workflows require users to navigate complex menus, understand algorithm parameters, and manually chain operations together. This creates a significant barrier for domain experts who understand \emph{what} they want to analyze but struggle with \emph{how} to express it in GIS software.

GeoSI addresses this gap by providing a natural language interface to GIS operations. Instead of navigating menus, users type queries like ``Buffer hospitals by 500 meters'' or ``Find schools within Kerala'' and the system automatically plans and executes the appropriate workflow.

\section{Problem Statement}
The core challenge is building a system that can:
\begin{enumerate}
\item Parse ambiguous natural language into precise GIS operations
\item Plan multi-step workflows that chain tools together correctly
\item Execute spatial algorithms across different environments (QGIS, standalone server, cloud)
\item Handle errors gracefully without crashing or producing incorrect results
\item Scale to support 127+ GIS tools across 12 intent categories
\end{enumerate}

\section{Objectives}
This project aims to:
\begin{itemize}
\item Design a three-surface architecture that separates the GIS ``brain'' from any specific platform
\item Implement a natural language parser with LLM support and deterministic fallback
\item Build a QGIS plugin that bridges the AI engine to the desktop GIS environment
\item Create a REST API server that operates independently of QGIS using pure Python spatial libraries
\item Demonstrate the system with real geospatial data (Kerala boundaries and school locations)
\end{itemize}

\section{Scope and Contributions}
The key contributions of this work are:
\begin{enumerate}
\item \textbf{Universal Engine Core:} A framework-free Python library with 127 GIS tools, an LLM-powered query parser, and an intelligent planning agent
\item \textbf{Backend Dispatch Pattern:} A novel architectural pattern that allows the same tool definitions to execute on QGIS Processing, GeoPandas, or any future backend
\item \textbf{Portable Backend:} Pure Python implementations of core spatial operations (buffer, clip, intersect, union, difference) using GeoPandas and Shapely
\item \textbf{Three-Surface Architecture:} Clean separation between the engine, QGIS plugin, and REST API
\end{enumerate}

\chapter{Literature Review and Related Work}

\section{GIS and Spatial Analysis}
Geographic Information Systems have evolved from simple map-making tools to comprehensive platforms for spatial analysis. QGIS, the leading open-source GIS, provides over 1,000 processing algorithms through its Processing framework. However, accessing these algorithms requires navigating nested menus and understanding parameter semantics.

\section{Natural Language Interfaces for GIS}
Research in natural language interfaces for databases (NLIDB) has shown that domain-specific parsers can achieve high accuracy when the vocabulary and grammar are constrained. GeoSI extends this approach to the GIS domain, where queries involve spatial relationships (``within,'' ``near,'' ``intersect''), distance specifications (``500 meters,'' ``2 km''), and layer references.

\section{Large Language Models in Geospatial Applications}
Recent advances in Large Language Models (LLMs) have enabled natural language understanding at unprecedented levels. Models like Mistral, LLaMA, and Gemini can parse complex instructions and generate structured output. GeoSI leverages these capabilities through a local-first approach using Ollama, with cloud providers as fallbacks.

\section{Microservice Architecture for GIS}
The trend toward microservice architectures in geospatial systems has been driven by the need for scalability and platform independence. OGC API standards define RESTful interfaces for geospatial data access. GeoSI's three-surface architecture aligns with this trend by separating the spatial intelligence engine from its delivery surfaces.

\section{GeoPandas and Shapely for Portable GIS}
GeoPandas extends the popular Pandas library with geospatial capabilities, while Shapely provides Python bindings to the GEOS geometry engine. Together, they enable high-performance spatial analysis without requiring a full GIS installation. GeoSI's portable backend builds on these libraries to achieve QGIS independence.

\chapter{System Architecture and Design}

\section{Overview}
GeoSI is built around three clean architectural surfaces that share a single universal engine:

\begin{enumerate}
\item \textbf{geosi\_engine/} --- The universal, framework-free core. No QGIS, no PyQt, no GDAL imports. Runs inside the plugin, a FastAPI server, Jupyter, or a test harness without modification.
\item \textbf{geosi\_plugin/} --- The QGIS desktop surface. The only code that imports \texttt{qgis} lives here.
\item \textbf{geosi\_server/} --- The optional REST surface (FastAPI). Prefers user-loaded layers and falls back to OpenStreetMap auto-fetch when a recognizable feature name is referenced but not loaded.
\end{enumerate}

\section{Design Principles}
Four rules keep the architecture clean:
\begin{enumerate}
\item The engine never imports QGIS.
\item The plugin only operates on layers already in the QGIS Layers panel and never auto-fetches data.
\item Ollama is first; everything else is a fallback.
\item Every failure path ends in a user-readable message, never a crash.
\end{enumerate}

\section{The Three Surfaces}

\end{table}

\section{Backend Dispatch Pattern}
\texttt{BackendTool} is the universal spec-carrying class used by almost every built-in tool. It never imports QGIS. Execution is delegated to a backend installed at runtime via \texttt{register\_backend(name, fn)}:

\begin{itemize}
\item Plugin startup calls \texttt{register\_backend("qgis", \_run\_qgis\_algorithm)}
\item Server startup calls \texttt{register\_backend("qgis", run\_portable\_algorithm)}
\end{itemize}

This keeps the engine exportable as a pure Python library.

\section{Data Flow: User Prompt to Result}
\begin{enumerate}
\item User types a natural language query
\item Parser extracts intent, entities, and parameters $\rightarrow$ \texttt{AnalysisRequest}
\item Agent plans the workflow $\rightarrow$ \texttt{ExecutionPlan}
\item Executor runs each step $\rightarrow$ \texttt{ExecutionResult}
\item Result is rendered to the user (chat dock or JSON response)
\end{enumerate}

\chapter{Engine Core Implementation}

\section{Data Models (models.py)}
The \texttt{models.py} module defines all data structures used throughout GeoSI. It has zero internal imports---it is the absolute foundation of the system. The module uses Python dataclasses instead of Pydantic for maximum compatibility.

\subsection{Enumerations}
Three enumerations define the system's type vocabulary:

\begin{itemize}
\item \textbf{ExecutionStatus:} SUCCESS, PARTIAL, FAILED, CANCELLED
\item \textbf{IntentType:} 12 categories---PROXIMITY, OVERLAY, GEOMETRY, RASTER, TERRAIN, NETWORK, TEMPORAL, AI\_ML, VALIDATION, STATISTICS, DATA\_MANAGEMENT, CARTOGRAPHY, UNKNOWN
\item \textbf{GeometryType:} POINT, LINESTRING, POLYGON, MULTIPOINT, MULTILINESTRING, MULTIPOLYGON, RASTER, UNKNOWN
\end{itemize}

\subsection{ToolParameter and ToolSpec}
\texttt{ToolParameter} describes one input a tool expects:
\begin{lstlisting}
@dataclass
class ToolParameter:
    name: str           # e.g., "distance"
    param_type: str     # "layer", "number", "string", "boolean"
    required: bool = True
    description: str = ""
    example: Optional[str] = None
    default: Optional[Any] = None
\end{lstlisting}

\texttt{ToolSpec} is the complete identity card of a tool---its name, description, category, parameters, and optional QGIS algorithm ID:
\begin{lstlisting}
@dataclass
class ToolSpec:
    name: str                    # Unique tool identifier
    display_name: str = ""
    description: str = ""
    category: str = "general"
    parameters: List[ToolParameter] = field(default_factory=list)
    qgis_algorithm: Optional[str] = None
    requires_qgis: bool = False
\end{lstlisting}

\subsection{Layer}
The \texttt{Layer} dataclass is the core data container. A Layer can represent either a vector dataset (GeoDataFrame in the \texttt{features} attribute) or a raster dataset (NumPy array in the \texttt{raster} attribute). The default CRS is EPSG:4326.

\subsection{AnalysisRequest}
The structured output of the parser. When the user types ``Find hospitals within 2km of flood zones,'' the parser produces:
\begin{lstlisting}
AnalysisRequest(
    query="Find hospitals within 2km of flood zones",
    intent=IntentType.PROXIMITY,
    entities={"primary_layer": "hospitals",
              "secondary_layer": "flood_zones"},
    parameters={"distance_value": 2000,
                "distance_unit": "meters"}
)
\end{lstlisting}

\subsection{ExecutionPlan and ToolStep}
An \texttt{ExecutionPlan} is an ordered list of \texttt{ToolStep} objects. Each step specifies which tool to run, with what parameters, and what the output should be called. Steps can declare dependencies on other steps via the \texttt{depends\_on} field.

\subsection{ExecutionResult and StepLog}
The \texttt{ExecutionResult} is the final product of the entire pipeline: success status, human-readable answer, step-by-step reasoning, output layers, and detailed execution logs with timing information.

\section{Tool Abstraction Layer (base.py)}
The \texttt{base.py} module defines three classes that form the tool contract:

\subsection{GISTool (Abstract Base Class)}
Every GIS tool must implement two methods:
\begin{itemize}
\item \texttt{spec()} --- Returns a \texttt{ToolSpec} describing the tool
\item \texttt{execute(**kwargs)} --- Performs the actual work and returns a \texttt{ToolResult}
\end{itemize}

The \texttt{safe\_execute()} wrapper handles parameter validation, timing, and exception catching automatically.

\subsection{PortableTool}
A \texttt{PortableTool} runs without any host framework. Tools like \texttt{LoadLayerTool}, \texttt{SaveLayerTool}, and \texttt{CleanLayerTool} inherit from this class and use GeoPandas directly.

\subsection{BackendTool --- The Universal Dispatch}
\texttt{BackendTool} is the most important architectural innovation. It carries the tool specification but delegates execution to a named backend installed at runtime:
\begin{lstlisting}
class BackendTool(GISTool):
    def execute(self, **kwargs) -> ToolResult:
        fn = get_backend(self._backend_name)
        if fn is None:
            return ToolResult(success=False,
                error="No backend registered")
        return fn(self._algorithm, parameters)
\end{lstlisting}

This pattern allows the same 127 tool definitions to work across three environments:
\begin{itemize}
\item \textbf{Plugin:} \texttt{register\_backend("qgis", \_run\_qgis\_algorithm)}
\item \textbf{Server:} \texttt{register\_backend("qgis", run\_portable\_algorithm)}
\item \textbf{Tests:} \texttt{register\_backend("qgis", mock\_algorithm)}
\end{itemize}

\section{Tool Registry (registry.py)}
The \texttt{ToolRegistry} auto-discovers all GIS tools at startup by walking through every module in \texttt{geosi\_engine/tools/} using Python's \texttt{pkgutil}. It finds all classes that inherit from \texttt{GISTool} and registers an instance of each.

After discovery, the registry exposes:
\begin{itemize}
\item \texttt{get\_tool(name)} --- Returns a tool instance by name
\item \texttt{list\_tools(category)} --- Lists all tool specs, optionally filtered
\item \texttt{execute\_tool(name, **kwargs)} --- Finds the tool and calls \texttt{safe\_execute()}
\end{itemize}

The registry discovers \textbf{127 tools} across 8 categories: vector (40), raster (25), terrain (10), network (8), temporal (6), AI/ML (10), cartography (10), validation (10), and portable (6).

\section{State Manager (state.py)}
The \texttt{StateManager} tracks all spatial layers, execution history, and intermediate results across the lifetime of a GeoSI session.

Key responsibilities:
\begin{enumerate}
\item \textbf{Layer tracking:} Maintain a \texttt{name $\rightarrow$ Layer} dictionary
\item \textbf{Result caching:} Store intermediate results so downstream steps can reference them
\item \textbf{Execution history:} Log every tool execution with timing
\item \textbf{CRS tracking:} Record the project CRS (default TEXTTT{EPSG:4326})
\item \textbf{Checkpoints:} Snapshot/rollback mechanism for undo operations
\end{enumerate}

When \texttt{save\_result()} receives a \texttt{ToolResult} containing a Layer, it automatically registers that layer in the workspace. This enables seamless step chaining.

\section{Validation Engine (validation.py)}
The \texttt{ValidationEngine} runs five categories of checks:
\begin{enumerate}
\item \textbf{Geometry:} Null, empty, and invalid geometry detection using vectorized operations
\item \textbf{CRS:} Missing CRS detection and cross-layer CRS mismatch warnings
\item \textbf{Attributes:} Required field existence checking
\item \textbf{Operation Preconditions:} Input layer availability, positive distance values
\item \textbf{Result:} Empty result warnings after tool execution
\end{enumerate}

\section{Conversation Manager (conversation.py)}
The \texttt{ConversationManager} maintains multi-turn dialogue history for interactive LLM sessions. It supports system prompts, message history trimming (max 20 turns), and JSON serialization for session persistence.

\chapter{Natural Language Processing Pipeline}

\section{Overview}
The \texttt{QueryParser} translates natural language GIS questions into structured \texttt{AnalysisRequest} objects. It runs as a layered pipeline that stays correct, deterministic, and cheap whenever possible, and reaches for LLMs only when genuinely needed.

\section{The Five-Layer Pipeline}
\begin{enumerate}
\item \textbf{Normalize:} Unicode normalization (NFKC), whitespace collapsing, em-dash replacement
\item \textbf{Cache Lookup:} In-process LRU cache (512 entries) keyed by SHA-256 hash of normalized query + available layers, plus optional on-disk JSON cache
\item \textbf{Keyword Parse:} Deterministic rule-based parser with weighted keyword matching. If it identifies a clear intent, the LLM is skipped entirely
\item \textbf{LLM Parse:} For ambiguous queries, try providers in order: Ollama $\rightarrow$ Gemini $\rightarrow$ Anthropic $\rightarrow$ OpenAI
\item \textbf{Post-Process:} Validate IntentType, normalize distance units to meters, backfill layers via fuzzy matching, cache the result
\end{enumerate}

\section{Intent Classification}
The keyword parser uses a weighted scoring system. Each keyword has a weight (1--3); higher weight means a stronger signal. The intent with the highest total score wins:

\begin{table}[h]
\centering
\begin{tabular}{lll}
\toprule
\textbf{Intent} & \textbf{High-Weight Keywords (3)} & \textbf{Medium-Weight (2)} \\
\midrule
PROXIMITY & buffer, closest, nearest, radius & within, near, distance \\
OVERLAY & intersect, clip, union, difference & combine, merge, overlap \\
GEOMETRY & centroid, simplify, dissolve & smooth, densify \\
RASTER & ndvi, ndwi, zonal, reclassify & pixel, band, satellite \\
TERRAIN & slope, aspect, hillshade, contour & elevation, terrain \\
NETWORK & shortest path, service area & route, driving \\
AI\_ML & cluster, classify, hotspot, kriging & density, predict \\
\bottomrule
\end{tabular}
\caption{Intent classification keyword weights}
\end{table}

Confidence is computed as: $\text{confidence} = \min(0.95,\; 0.35 + 0.6 \times \frac{\text{top\_score}}{\text{total\_signal}})$

\section{Distance Extraction and Unit Conversion}
The parser uses a regular expression to extract distance values with units and automatically converts to meters:

\begin{lstlisting}
_UNIT_TO_METERS = {
    "m": 1.0, "km": 1000.0, "mi": 1609.344,
    "ft": 0.3048, "yd": 0.9144, "nmi": 1852.0,
}
# "Buffer schools by 2 km" -> distance_value=2000
\end{lstlisting}

\section{Fuzzy Layer Matching}
The parser uses Python's \texttt{SequenceMatcher} for fuzzy matching of layer names against the query text. The matching pipeline:
\begin{enumerate}
\item Exact substring match (score 1.0)
\item Stem match---e.g., ``school'' matches ``Schools'' (score 0.85)
\item \texttt{SequenceMatcher} ratio $\geq 0.72$ (computed score)
\end{enumerate}

Results are cached in a thread-safe LRU cache (256 entries) to avoid recomputing for repeated queries.

\section{Operation Detection}
The parser identifies specific GIS operations using an operation map:
\begin{lstlisting}
_OPERATION_MAP = {
    "buffer": ["buffer", "grow by", "ring around"],
    "clip": ["clip", "cut to", "crop", "extract", "subset"],
    "intersect": ["intersect", "overlap", "common area"],
    "ndvi": ["ndvi", "vegetative index", "vegetation"],
    "slope": ["slope"],
    "join_attributes": ["join", "attribute join"],
}
\end{lstlisting}

When a well-understood operation is detected, the LLM is bypassed entirely for faster, more reliable execution.

\section{LLM Prompting Strategy}
For ambiguous queries where keywords return UNKNOWN, the parser sends a structured JSON-schema prompt to the LLM:
\begin{lstlisting}
"You are GeoSI, a geospatial intelligence query parser.
 Convert the user's GIS question into a STRICT JSON object.
 Return ONLY JSON. No markdown, no prose, no code fences.
 Available layers: [Kerala, Schools]
 Valid intents: [proximity, overlay, geometry, ...]
 User query: 'Find areas of interest'"
\end{lstlisting}

The response is parsed with tolerant JSON extraction that handles markdown code fences, partial JSON, and greedy balanced-brace matching.

\section{CRS and Projection Handling}
The parser detects CRS references using the pattern \texttt{EPSG[:\textbackslash s]?(\textbackslash d\{4,6\})}. When found, the CRS is stored in \texttt{parameters["crs"]}. The default workspace CRS is EPSG:4326 (WGS 84).

\chapter{AI Planning Agent}

\section{Overview}
The \texttt{GeoSIAgent} converts a parsed \texttt{AnalysisRequest} into an \texttt{ExecutionPlan}. It uses a priority chain of LLM providers with a comprehensive rule-based fallback.

\section{Planning Priority}
\begin{enumerate}
\item For well-understood operations (clip, buffer, intersect, slope, ndvi), the rule-based planner is used directly---no LLM call
\item For complex queries, try Ollama $\rightarrow$ Gemini $\rightarrow$ Anthropic
\item If all LLMs fail, the rule-based planner handles the request
\end{enumerate}

\section{Layer Validation}
Before planning, the agent validates that all referenced layers exist:
\begin{lstlisting}
def validate_layers_exist(self, request, state):
    available = state.list_layers()
    primary = request.entities.get("primary_layer")
    if primary not in available:
        similar = self.find_similar_layers(primary, available)
        if similar:
            return False, f"Did you mean: {similar}?"
        return False, f"Layer '{primary}' not found."
\end{lstlisting}

The fuzzy matching uses \texttt{SequenceMatcher} with a 0.5 threshold and case-insensitive comparison.

\section{Rule-Based Planning}
The rule-based planner maps intents to default tool sequences:
\begin{lstlisting}
_DEFAULT_PLANS = {
    IntentType.PROXIMITY: ["buffer", "intersect"],
    IntentType.OVERLAY:   ["intersect"],
    IntentType.GEOMETRY:  ["clean_layer"],
    IntentType.RASTER:    ["raster_calc"],
    IntentType.TERRAIN:   ["slope"],
}
\end{lstlisting}

For each tool in the sequence, the planner:
\begin{enumerate}
\item Maps the primary layer to the first required parameter
\item Maps the secondary layer to OVERLAY (for overlays) or INPUT\_2 (for joins)
\item Maps distance values to the DISTANCE parameter (for buffer)
\item Generates descriptive step names
\end{enumerate}

\section{LLM Plan Validation}
After an LLM generates a plan, the agent validates it:
\begin{itemize}
\item All tool names must exist in the registry
\item All layer references must match loaded layers
\item Numeric values and output references are allowed
\item Step dependencies must reference existing steps
\end{itemize}

\section{Error Recovery}
When a step fails during execution, \texttt{recover\_from\_error()} drops the failed step and any steps that depend on it (transitively), producing a reduced but valid plan.

\chapter{Execution Engine}

\section{Overview}
The \texttt{ExecutionEngine} runs an \texttt{ExecutionPlan} step by step, wiring the output of each step to the input of the next.

\section{Execution Flow}
\begin{enumerate}
\item Iterate through each \texttt{ToolStep} in the plan
\item Build resolved parameters by substituting:
  \begin{itemize}
  \item Previous step output references with actual results
  \item Layer name strings with Layer objects from state
  \end{itemize}
\item Call the tool via \texttt{registry.execute\_tool()}
\item Store the result in state for downstream steps
\item Create a \texttt{StepLog} with timing and feature count
\end{enumerate}

\section{Partial Execution}
If a step fails, the executor does NOT abort. It marks success as false, logs the error, and continues with remaining steps. The final status is:
\begin{itemize}
\item \textbf{SUCCESS:} All steps completed successfully
\item \textbf{PARTIAL:} Some steps succeeded, some failed
\item \textbf{FAILED:} All steps failed
\end{itemize}

\section{Answer Generation}
The executor generates two human-readable outputs:
\begin{itemize}
\item \textbf{Answer:} A one-line summary with emoji indicator (checkmark, warning, or X)
\item \textbf{Reasoning:} Step-by-step log with timing, feature counts, and error details
\end{itemize}

\chapter{QGIS Plugin Implementation}

\section{Overview}
The \texttt{geosi\_plugin} is the QGIS desktop surface. It is the ONLY code that imports \texttt{qgis} or \texttt{PyQt}. This strict isolation ensures the universal engine remains portable.

\section{Plugin Entry Point}
QGIS discovers plugins by calling \texttt{classFactory(iface)} in \texttt{\_\_init\_\_.py}. This returns an instance of \texttt{GeoSIPlugin}, which receives the QGIS interface object providing access to the main window, message bar, map canvas, and layer tree.

\section{Main Plugin Class (geosi\_plugin.py)}
The \texttt{GeoSIPlugin} manages the plugin lifecycle:

\subsection{initGui()}
Called once when QGIS loads the plugin. It performs three tasks:
\begin{enumerate}
\item Calls \texttt{qgis\_bridge.install()} to register the QGIS Processing backend
\item Creates a \texttt{QAction} with the GeoSI icon and connects it to \texttt{toggle\_dock()}
\item Adds the action to both the toolbar and the Plugins menu
\end{enumerate}

\subsection{toggle\_dock()}
Creates the \texttt{GeoSIDock} widget on first click and toggles visibility on subsequent clicks. The dock is placed in the right dock area.

\subsection{Qt5/Qt6 Compatibility}
The plugin detects the Qt version at runtime to resolve the correct dock area enum:
\begin{lstlisting}
def _resolve_right_dock_area(self):
    area = getattr(Qt, 'RightDockWidgetArea', None)  # Qt5
    if area is None:
        dock_enum = getattr(Qt, 'DockWidgetArea', None)  # Qt6
        area = getattr(dock_enum, 'RightDockWidgetArea')
    return area
\end{lstlisting}

\section{QGIS Backend Bridge (qgis\_bridge.py)}
This is the most architecturally significant file in the plugin. It registers a callable that wraps \texttt{processing.run()} and makes it available to the engine:

\begin{lstlisting}
def _run_qgis_algorithm(algorithm_id, parameters):
    import processing  # QGIS runtime only
    result = processing.run(algorithm_id, parameters)
    return ToolResult(success=True, output=result)

def install():
    register_backend("qgis", _run_qgis_algorithm)
\end{lstlisting}

After \texttt{install()} is called, every \texttt{BackendTool} in the engine dispatches to QGIS Processing. The engine has zero knowledge of QGIS---it only knows it has a callable named ``qgis.''

\section{Interactive Chat Dock (prompt\_dock.py)}
The \texttt{GeoSIDock} provides the chat interface with the following components:
\begin{itemize}
\item \texttt{QTextBrowser} for displaying chat messages with HTML formatting
\item \texttt{QLineEdit} for typing queries
\item \texttt{QPushButton} for submission
\item Collapsible LLM settings panel for Ollama configuration
\item ``Test Ollama'' button that pings \texttt{/api/tags}
\end{itemize}

\section{Layer Synchronization}
Before every query, the dock synchronizes the QGIS Layers panel with the engine's \texttt{StateManager}:

def _sync_qgis_layers(self):
    qgis_layers = QgsProject.instance().mapLayers()

\chapter{Universal REST API Server}

\section{Overview}
The \texttt{geosi\_server} wraps the universal engine in a FastAPI web server. It runs completely independently of QGIS by registering a Portable Backend that intercepts QGIS algorithm calls and executes them in pure Python.

\section{Server Architecture}
The server follows a three-tier architecture:
\begin{enumerate}
\item \textbf{Web Tier:} FastAPI routes validate requests using Pydantic schemas
\item \textbf{Service Tier:} \texttt{ToolService} bridges API calls to the engine
\item \textbf{Engine Tier:} The \texttt{geosi\_engine} performs all spatial reasoning
\end{enumerate}

\section{Entry Point (main.py)}
The \texttt{main.py} file initializes the FastAPI app with two critical setup tasks:

\subsection{Portable Backend Registration}
\begin{lstlisting}
from geosi_engine.base import register_backend
from geosi_engine.backends.portable import run_portable_algorithm

register_backend("qgis", run_portable_algorithm)
\end{lstlisting}

This single line makes the server universal. By registering \texttt{run\_portable\_algorithm} under the name ``qgis,'' every \texttt{BackendTool} routes to GeoPandas implementations.

\subsection{CORS Configuration}
Cross-Origin Resource Sharing is enabled for web frontend integration.

\section{Tool Service Layer}
The \texttt{ToolService} bridges the web tier to the engine. It wraps every operation in a single-step \texttt{ExecutionPlan} and delegates to the engine's executor:

\begin{lstlisting}
def _run_tool(self, tool_name, params, output_name=None):
    step = ToolStep(tool_name=tool_name, parameters=params)
    plan = ExecutionPlan(steps=[step])
    result = self._engine.executor.run(plan)
    return OperationResponse(success=result.success, ...)
\end{lstlisting}

\section{Event-Driven State Synchronization}
The \texttt{WorkspaceState} uses a listener pattern to sync mutations:
\begin{lstlisting}
self.state.add_listener(self._on_workspace_event)

def _on_workspace_event(self, event, name, layer):
    if event in ("added", "replaced"):
        self._engine.state.add_layer(layer)
    elif event == "removed":
        self._engine.state.remove_layer(name)
\end{lstlisting}

\section{OSM Auto-Fetcher}
When a query references a feature not loaded in the workspace, the server attempts to download it from OpenStreetMap Overpass API. This ONLY happens in the server surface---the QGIS plugin never auto-fetches.

\section{Persistence and Caching}
Three caching layers optimize performance:
\begin{itemize}
\item \textbf{GeoJSON Cache:} Keyed by (layer, version, bbox, tolerance, limit)
\item \textbf{Validation Cache:} Keyed by (layer, version)
\item \textbf{Telemetry:} Execution timing for bottleneck analysis
\end{itemize}

def run_buffer(parameters):
    gdf = layer.features  # GeoDataFrame
    distance = parameters.get("DISTANCE", 100)
    buffered = gdf.copy()
    buffered["geometry"] = gdf.geometry.buffer(distance)
    if parameters.get("DISSOLVE"):
        buffered = buffered.dissolve()
    return Layer(name=f"{layer.name}_buffer",
                 features=buffered, ...)
\end{lstlisting}

\chapter{Conclusions and Future Work}

\section{Summary of Contributions}
This project has successfully designed and implemented GeoSI, a conversational AI system for geospatial analysis. The key contributions are:

\begin{enumerate}
\item \textbf{Three-Surface Architecture:} Clean separation of the universal engine, QGIS plugin, and REST API server, enabling deployment across multiple platforms without code duplication.

\item \textbf{Backend Dispatch Pattern:} A novel architectural pattern that allows 127 tool definitions to execute on QGIS Processing, GeoPandas, or any future backend through runtime registration.

\item \textbf{Natural Language Pipeline:} A five-layer parsing pipeline with LRU caching, weighted keyword scoring, multi-provider LLM support, and deterministic fallback that ensures reliable operation in both online and offline environments.

\item \textbf{Portable Backend:} Pure Python implementations of core spatial operations (buffer, clip, intersect, union, difference) using GeoPandas and Shapely, enabling QGIS-independent spatial analysis.

\item \textbf{Event-Driven State Management:} Workspace state synchronization using listener patterns that eliminate expensive full-sync loops.
\end{enumerate}

\section{Lessons Learned}
\begin{itemize}
\item \textbf{LLM Reliability:} LLMs frequently hallucinate tool names and layer references. The post-validation step that checks LLM output against the actual registry and loaded layers is essential.
\item \textbf{Keyword First:} For well-understood operations like buffer, clip, and intersect, the deterministic keyword parser is both faster and more accurate than LLM-based parsing.
\item \textbf{CRS Matters:} Automatic CRS alignment in the portable backend prevents the most common spatial analysis error---empty results from CRS-mismatched overlays.
\item \textbf{Partial Execution:} Continuing execution after a step fails (rather than aborting) provides more useful results and better error diagnostics.
\end{itemize}

\section{Limitations}
\begin{itemize}
\item The portable backend currently implements only 5 of the 127 tools. Complex operations (network analysis, raster processing) still require QGIS.
\item The parser's keyword system may misclassify novel query patterns that don't match any predefined keywords.
\item Multi-step plans generated by LLMs are not always optimal and may include unnecessary steps.
\end{itemize}

\section{Future Work}
\begin{enumerate}
\item \textbf{Complete Portable Coverage:} Implement all 127 tools in pure Python for complete QGIS independence.
\item \textbf{Domain-Specific LLM:} Fine-tune a small language model specifically for GIS workflow planning using a curated dataset of query-plan pairs.
\item \textbf{Web Dashboard:} Build a React/Vue frontend that consumes the REST API and provides map visualization.
\item \textbf{Distributed Processing:} Extend the executor to support parallel step execution for independent tool chains.
\item \textbf{Raster Backend:} Implement portable raster operations using Rasterio and NumPy.
\item \textbf{Authentication:} Add OAuth2 authentication for multi-user server deployments.
\end{enumerate}

\section{Is This the Foundation of Geospatial Superintelligence?}
Yes. GeoSI establishes the architectural foundation for geospatial superintelligence by demonstrating that:
\begin{itemize}
\item Spatial reasoning can be decoupled from any specific GIS platform
\item Natural language can serve as the primary interface for complex spatial analysis
\item LLM-powered planning can orchestrate multi-step GIS workflows
\item A portable backend can execute spatial operations without heavy dependencies
\end{itemize}

The path from this foundation to true geospatial superintelligence involves scaling the tool coverage, improving the planning agent's ability to handle complex multi-step workflows, and integrating real-time data streams. But the core architecture---parse, plan, execute, with pluggable backends and graceful degradation---is the right foundation to build upon.
