1. Introduction
Building a domain-specific Large Language Model (LLM) for Geoinformatics requires a carefully designed pipeline that combines two powerful techniques: fine-tuning and Retrieval-Augmented Generation (RAG). This document provides a complete, end-to-end technical workflow to guide you through every stage — from data collection to deployment.

1.1 Why Combine Fine-Tuning and RAG?
Fine-tuning alone improves the model's understanding of geospatial language, concepts, and tasks — but it cannot keep up with ever-growing spatial datasets, new publications, or dynamic geospatial APIs. RAG solves this by letting the model retrieve relevant, up-to-date information at inference time without retraining.

What It Solves

	•	Coordinate reference system (CRS) reasoning and transformation
	•	Automated GIS workflow scripting (QGIS, ArcGIS, GDAL)
	•	Toponym recognition and georeferencing
	•	Satellite imagery analysis and NDVI/NDWI explanation
	•	Spatial relationship detection and site selection
	•	GeoJSON / Shapefile description and validation


2. System Architecture Overview
The complete Geoinformatics LLM system has two parallel pipelines: an offline pipeline for training the fine-tuned model, and an online pipeline for serving queries at runtime with RAG augmentation.

2.1 The Two Pipelines
Offline Pipeline Data collection → preprocessing → fine-tuning → model registry. This runs once (or periodically). Output is a fine-tuned model checkpoint.

Online Pipeline (RAG) User query → query understanding → vector retrieval → context injection → fine-tuned LLM → response → GIS tool execution (optional).

PHASE 01    Data Collection & Curation

3.1 Data Categories
Geoinformatics LLM training requires two distinct types of data that serve different purposes in the pipeline:

3.1.1 Domain Pre-Training Corpus (Large-Scale Unlabeled Text)
This large corpus is used for Domain-Adaptive Pre-Training (DAPT) — a continued pre-training step that deepens the model's geospatial vocabulary before instruction tuning begins.
	•	GIS academic papers: ISPRS journals, AGU publications, arXiv (cs.CV, cs.AI with geo tags)
	•	OpenStreetMap wiki, documentation, and tagging guides
	•	ESRI ArcGIS documentation and help articles
	•	QGIS official documentation (all versions)
	•	OGC (Open Geospatial Consortium) standards and specifications
	•	Copernicus, USGS, and NASA EarthData portal content
	•	Wikipedia articles on geographic regions, projections, and GIS concepts
	•	Remote sensing textbooks and lecture notes (open access)
	•	GIS Stack Exchange Q&A threads

3.1.2 Instruction-Tuning Dataset (Supervised Pairs)
These are the (instruction, response) pairs used for supervised fine-tuning. Each pair must represent a realistic geospatial task that a GIS professional might request.

Example instruction-response pairs:
Instruction (User)
Expected Response
Write a PostGIS query to find all schools within 500m of a flood zone
SELECT s.name FROM schools s JOIN flood_zones f ON ST_DWithin(s.geom, f.geom, 500) WHERE f.risk_level = 'high';
What does a negative NDVI value mean in a Sentinel-2 image?
Negative NDVI (< 0) typically indicates water bodies, snow, ice, or bare rock — areas with little to no vegetation...
Explain the difference between EPSG:4326 and EPSG:3857
EPSG:4326 is WGS84 geographic coordinates (lat/lon in degrees). EPSG:3857 is Web Mercator (projected, meters). Use 4326 for storage, 3857 for web mapping...
Convert a Shapefile to GeoJSON using GDAL
ogr2ogr -f GeoJSON output.geojson input.shp -t_srs EPSG:4326
What is a spatial join and how do I perform one in GeoPandas?
A spatial join combines two datasets based on their geometric relationship... gdf_result = gpd.sjoin(gdf_left, gdf_right, how='inner', predicate='intersects')

Data Quality Rule Quality over quantity is critical. Research shows that 1,000 carefully curated geo instruction pairs outperform 10,000 noisy examples. Every pair must be geographically accurate and syntactically correct.

3.3 Data Preprocessing Pipeline
Raw collected data must go through a strict preprocessing pipeline before training:
	•	Deduplication: Remove exact and near-duplicate texts using MinHash LSH or SimHash
	•	Language filtering: Keep only English text (or your target language) using langdetect
	•	Quality filtering: Remove short texts (<50 words), broken HTML, encoding errors
	•	Geo relevance scoring: Use a small classifier or keyword filter to keep geo-relevant content
	•	Format standardization: Convert all instruction pairs to a consistent JSON schema
	•	Train/validation/test split: 80% train, 10% validation, 10% test — stratified by task type

Standard JSON format for instruction pairs (Alpaca format):
{ "instruction": "...", "input": "", "output": "..." }
Or ShareGPT format (for multi-turn conversation datasets):
{ "conversations": [{"from": "human", "value": "..."}, {"from": "gpt", "value": "..."}] }

PHASE 03    Fine-Tuning the GeoLLM

5.1 Fine-Tuning Strategy: DAPT then SFT
The recommended training sequence has two stages:
	•	Domain-Adaptive Pre-Training (DAPT): Continue pre-training on large-scale geo text corpus to deepen geospatial vocabulary. Optional — skip if dataset is small (<1GB).
	•	Supervised Fine-Tuning (SFT): Fine-tune on instruction-response pairs using QLoRA for efficiency.

GTChain Finding Research from the GTChain project demonstrated that fine-tuning LLaMA-2-7B on geospatial instruction data achieved 32.5% higher accuracy than GPT-4 on geospatial tool-use tasks — proving that domain fine-tuning is highly effective.

5.2 QLoRA: The Standard Technique
QLoRA (Quantized Low-Rank Adaptation) is the standard technique for fine-tuning LLMs in resource-constrained environments. It combines two innovations:
	•	4-bit quantization (bitsandbytes): Reduces the base model's memory footprint by 4x, so a 7B model fits in ~5GB VRAM instead of ~14GB.
	•	LoRA adapters: Instead of updating all parameters, LoRA adds small trainable matrices (rank-r adapters) to the attention layers. Only these adapters are trained — far fewer parameters, faster training, no catastrophic forgetting.

5.3 Full Fine-Tuning Pipeline (Step-by-Step)

Step 1: Environment Setup
pip install transformers peft bitsandbytes trl datasets accelerate wandb
# Optional but recommended for monitoring
pip install wandb  # Weights & Biases for experiment tracking

Step 2: Load Base Model with 4-bit Quantization
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
import torch

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_use_double_quant=True,
    bnb_4bit_quant_type='nf4',
    bnb_4bit_compute_dtype=torch.bfloat16
)

model = AutoModelForCausalLM.from_pretrained(
    'meta-llama/Meta-Llama-3.1-8B',
    quantization_config=bnb_config,
    device_map='auto'
)
tokenizer = AutoTokenizer.from_pretrained('meta-llama/Meta-Llama-3.1-8B')

Step 3: Configure LoRA Adapters
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training

model = prepare_model_for_kbit_training(model)

lora_config = LoraConfig(
    r=16,                    # LoRA rank — higher = more capacity
    lora_alpha=32,           # Scaling factor (usually 2x rank)
    target_modules=['q_proj', 'k_proj', 'v_proj', 'o_proj'],
    lora_dropout=0.05,
    bias='none',
    task_type='CAUSAL_LM'
)
model = get_peft_model(model, lora_config)

Step 4: Prepare the Geospatial Dataset
from datasets import load_dataset

dataset = load_dataset('json', data_files={
    'train': 'geo_instructions_train.json',
    'validation': 'geo_instructions_val.json'
})

# Format into prompt template
def format_prompt(example):
    return {'text': f"### Instruction:\n{example['instruction']}\n
                          ### Response:\n{example['output']}"}
dataset = dataset.map(format_prompt)

Step 5: Training with SFTTrainer
from trl import SFTTrainer
from transformers import TrainingArguments

training_args = TrainingArguments(
    output_dir='./geo_llm_checkpoints',
    num_train_epochs=3,
    per_device_train_batch_size=4,
    gradient_accumulation_steps=4,   # Effective batch size = 16
    learning_rate=2e-4,
    warmup_ratio=0.05,
    lr_scheduler_type='cosine',
    fp16=False,
    bf16=True,                        # Use bfloat16 for stability
    logging_steps=25,
    save_steps=200,
    evaluation_strategy='steps',
    eval_steps=200,
    load_best_model_at_end=True,
    report_to='wandb'
)

trainer = SFTTrainer(
    model=model,
    train_dataset=dataset['train'],
    eval_dataset=dataset['validation'],
    dataset_text_field='text',
    tokenizer=tokenizer,
    args=training_args,
    max_seq_length=2048
)
trainer.train()

Step 6: Save the Fine-Tuned Adapter
model.save_pretrained('./geo_llm_adapter')
tokenizer.save_pretrained('./geo_llm_adapter')

PHASE 04    Building the RAG Pipeline

6.1 RAG Architecture for Geoinformatics
Retrieval-Augmented Generation (RAG) allows the fine-tuned GeoLLM to access a large, dynamic knowledge base at inference time — without retraining. This is especially valuable for geoinformatics because the knowledge base can include live spatial datasets, updated documentation, and project-specific GIS data.

The RAG pipeline has four stages: Indexing, Retrieval, Augmentation, and Generation.

6.2 Stage 1 — Knowledge Base Indexing
This is an offline stage that prepares the searchable knowledge base. It runs once and is updated when new geo documents are added.

Step 1: Choose and Embed Documents
Index the following geo document types into the vector database:
	•	GIS API references (QGIS PyQGIS docs, GDAL C++ and Python API docs)
	•	PostGIS and spatial SQL function references
	•	OGC standards (WMS, WFS, WCS, WPS specifications)
	•	Remote sensing product guides (Sentinel-2, Landsat band descriptions)
	•	Coordinate reference system references (EPSG registry)
	•	Your own project-specific GIS data dictionaries and metadata
	•	Academic papers relevant to your use case

Step 2: Chunking Strategy
Proper chunking is critical for retrieval quality. Use semantic chunking rather than fixed-size:
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,          # ~512 tokens per chunk
    chunk_overlap=64,        # Overlap prevents context loss at boundaries
    separators=['\n\n', '\n', '. ', ' ']
)
chunks = splitter.split_documents(geo_documents)

Step 3: Embedding the Chunks
Use a sentence-transformer model to convert text chunks into dense vector embeddings:
from sentence_transformers import SentenceTransformer

# Use a high-quality embedding model
embed_model = SentenceTransformer('BAAI/bge-large-en-v1.5')
# Or for geo-specific, try: 'intfloat/e5-large-v2'

embeddings = embed_model.encode(
    [chunk.page_content for chunk in chunks],
    batch_size=64,
    show_progress_bar=True
)

Step 4: Store in Vector Database
import chromadb

client = chromadb.PersistentClient(path='./geo_vector_db')
collection = client.create_collection('geo_knowledge')

collection.add(
    embeddings=embeddings.tolist(),
    documents=[c.page_content for c in chunks],
    metadatas=[{'source': c.metadata.get('source', ''), 'type': c.metadata.get('type', '')} for c in chunks],
    ids=[f'chunk_{i}' for i in range(len(chunks))]
)

6.3 Stage 2 — Query-Time Retrieval
At inference time, when a user sends a geospatial query, the retriever finds the most relevant knowledge chunks and injects them into the prompt.

Retrieval Step-by-Step
	•	Embed the user query using the same embedding model used during indexing.
	•	Search the vector database for the top-k most similar chunks (cosine similarity).
	•	Apply optional metadata filters (e.g., only retrieve PostGIS docs if query contains SQL keywords).
	•	Re-rank results using a cross-encoder for higher precision (optional but recommended).
	•	Select the top 3–5 chunks that fit within the context window.

def retrieve_geo_context(query, collection, embed_model, top_k=5):
    query_embedding = embed_model.encode([query])[0]
    results = collection.query(
        query_embeddings=[query_embedding.tolist()],
        n_results=top_k,
        include=['documents', 'metadatas', 'distances']
    )
    return results['documents'][0]  # List of relevant text chunks

6.4 Stage 3 — Prompt Augmentation
Combine the retrieved context with the user query to build the final prompt for the GeoLLM. The system prompt must instruct the model on how to use the retrieved context.

GEO_SYSTEM_PROMPT = '''You are GeoLLM, a geospatial AI assistant expert in GIS,
remote sensing, spatial databases, and geoinformatics.

Use the following retrieved context from your knowledge base to answer
accurately. If the context does not contain the answer, say so — do not
hallucinate geographic facts.

RETRIEVED CONTEXT:
{context}

Answer the user's geospatial question with precision and include
working code examples where applicable.'''

def build_geo_prompt(query, context_chunks):
    context_text = '\n\n---\n\n'.join(context_chunks)
    return GEO_SYSTEM_PROMPT.format(context=context_text) + f'\n\nUser: {query}'

6.5 Stage 4 — Generation with the Fine-Tuned GeoLLM
The augmented prompt is passed to the fine-tuned GeoLLM for generation. The model produces answers grounded in both its fine-tuned geospatial knowledge and the retrieved context.

from peft import PeftModel
from transformers import pipeline

# Load fine-tuned model
base = AutoModelForCausalLM.from_pretrained('meta-llama/Meta-Llama-3.1-8B', ...)
geo_model = PeftModel.from_pretrained(base, './geo_llm_adapter')

# Inference pipeline
pipe = pipeline('text-generation', model=geo_model, tokenizer=tokenizer,
                max_new_tokens=512, temperature=0.1, do_sample=True)

def geo_llm_answer(query):
    context = retrieve_geo_context(query, collection, embed_model)
    prompt = build_geo_prompt(query, context)
    response = pipe(prompt)[0]['generated_text']
    return response

8.4 Evaluation Code Example
def evaluate_sql_generation(model, test_pairs, db_connection):
    valid = 0
    correct = 0
    for pair in test_pairs:
        generated_sql = model.generate(pair['instruction'])
        try:
            result = db_connection.execute(generated_sql)
            valid += 1
            if result == pair['expected_result']:
                correct += 1
        except Exception:
            pass  # Invalid SQL — not counted
    print(f'Validity: {valid/len(test_pairs):.2%}')
    print(f'Correctness: {correct/len(test_pairs):.2%}')

9.3 Complete Inference Pipeline (Production)
# Full RAG + GeoLLM inference endpoint (FastAPI)
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI(title='GeoLLM API')

class GeoQuery(BaseModel):
    query: str
    use_tools: bool = False

@app.post('/geo-query')
async def geo_query(request: GeoQuery):
    # 1. Retrieve relevant geo knowledge
    context = retrieve_geo_context(request.query, collection, embed_model)
    # 2. Build augmented prompt
    prompt = build_geo_prompt(request.query, context)
    # 3. Generate response with fine-tuned GeoLLM
    response = geo_model_generate(prompt)
    # 4. Optionally execute any GIS code in the response
    if request.use_tools:
        response = tool_executor.run(response)
    return {'response': response, 'sources': [c[:100] for c in context]}

12. Common Pitfalls & How to Avoid Them

Pitfall
How to Avoid It
Training data contains incorrect geo facts (wrong CRS, bad SQL)
Have domain experts manually review at least 10% of instruction pairs before training
Model hallucinates spatial relationships
Include topology classification examples in training; use RAG to ground factual claims
RAG retrieves irrelevant chunks
Use metadata filters + cross-encoder re-ranking; tune chunk size and overlap
Overfitting on small instruction dataset
Use LoRA dropout 0.1, stop early when validation loss increases, limit epochs to 3
Generated SQL fails on real PostGIS schema
Include your actual table schema in the system prompt; fine-tune on schema-aware examples
Context window overflow with RAG
Limit to top-3 chunks; use summarization for long documents before indexing
Slow inference in production
Quantize to Q4_K_M GGUF; use vLLM with continuous batching for throughput
Model forgets general language ability after fine-tuning
Use QLoRA (not full fine-tuning); it preserves base model weights

13. Recommended Next Steps
	•	Start small: Collect 500–1000 high-quality geospatial instruction pairs as your MVP dataset.
	•	Fine-tune LLaMA 3.1 8B with QLoRA on a single RTX 3090 — this is achievable in 2–6 hours.
	•	Build a minimal RAG pipeline with ChromaDB and your most important geo documents (start with PostGIS and QGIS docs).
	•	Evaluate on a 100-example holdout set with a mix of SQL generation, spatial QA, and CRS tasks.
	•	Iterate on data quality first — adding more instruction pairs yields faster gains than changing model size.
	•	Deploy locally with Ollama for testing, then move to vLLM when production traffic demands it.
	•	Integrate the tool-use layer once the base model + RAG is working well.

Final Tip The GeoLLM + RAG hybrid outperforms either approach alone. Fine-tuning gives deep domain expertise; RAG gives factual accuracy and freshness. Together, they produce a system more reliable than using a general-purpose LLM like GPT-4 for geoinformatics tasks — as proven by GTChain, GeoGPT, and BB-GeoGPT research.
